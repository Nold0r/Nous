## Высокий приоритет

### S01. [P1, Б] Уязвимая версия protobuf в рабочем Windows-пути

`crates/nous-hsr/Cargo.toml`, `vendor/reliquary/Cargo.toml`, корневой `Cargo.lock`: зафиксирован `protobuf = 3.7.1`. [RUSTSEC-2024-0437](https://rustsec.org/advisories/RUSTSEC-2024-0437.html) / CVE-2025-53605 описывает переполнение стека при разборе неизвестных полей; исправленная версия — `>=3.7.2`. Здесь protobuf разбирает сетевые данные, то есть недоверенный ввод действительно доходит до библиотеки. Специально переполнение стека не вызывалось.

Обновление требует согласовать runtime, `protobuf-json-mapping`, pin в reliquary и сгенерированный код с проверкой `VERSION_3_7_1`. Одного изменения версии в manifest приложения недостаточно.

### S02. [P1, Т+К] Короткий сетевой пакет вызывает panic и оставляет неверный статус

Код: [connection.rs:33](../../../../Nous-sdk/vendor/reliquary/src/network/connection.rs#L33), [crypto.rs:21](../../../../Nous-sdk/vendor/reliquary/src/network/crypto.rs#L21), [network/mod.rs:216](../../../../Nous-sdk/vendor/reliquary/src/network/mod.rs#L216); обработчик в [nous-hsr/src/lib.rs:99](../../../../Nous-sdk/crates/nous-hsr/src/lib.rs#L99).

Воспроизведены три случая: UDP payload длиной 4 байта попадает в `payload[4..8]`; KCP-команда длиной 1 байт — в `bytes[..4]`; корректная оболочка token-команды с испорченным protobuf — в `parse_proto().unwrap()`. Программа фильтрует порты, но не доказывает принадлежность пакета игровому процессу.

В SDK захват живёт в отдельном потоке. Внешний обработчик переводит статус в `Error` только для `Err`, а panic проходит мимо этой ветви. Захват завершается, статус может остаться `Connected`/`WaitingForLogin`. Это отказ захвата, не доказанное выполнение произвольного кода. В тесте token-парсера использован искусственный известный ключ; сетевой доступ атакующего к реальной сессии отдельно не доказывался.

Исправление: проверки длины до индексации, отказ без panic, обработка повреждённого token, наблюдение за аварийным завершением worker и явный путь восстановления.

### S03. [P1, Т] Отказ сервера применяется как успешные данные

Код: [decode.rs:9](../../../../Nous-sdk/crates/nous-hsr/src/decode.rs#L9), [decode.rs:48](../../../../Nous-sdk/crates/nous-hsr/src/decode.rs#L48), [nous-hsr/src/world.rs](../../../../Nous-sdk/crates/nous-hsr/src/world.rs).

`retcode` не проверяется перед преобразованием ответов. Тесты показывают:

- `GetBagScRsp { retcode: 1, relic_list: [] }` стирает ранее корректный инвентарь;
- отказной `PlayerGetTokenScRsp` с UID по умолчанию переключает аккаунт на **0**;
- отказной `InteractPropScRsp` заменяет сохранённое состояние объекта на **0**.

Ошибочные изменения затем сохраняются обычным saver. Проверять успешность ответа и допустимый UID нужно в HSR-декодере, до формирования доменной команды. Проверить аналогичные response-ветви, включая баннеры, сцены и снимки.

### S04. [P1, Т+К] Нет привязки доменных изменений к подтверждённой игровой сессии

Код: [sniffer.rs:63](../../../../Nous-sdk/crates/nous-hsr/src/sniffer.rs#L63), [game.rs:153](../../../../Nous-sdk/crates/nous-core/src/game.rs#L153).

Загружается последний аккаунт, а затем любой декодированный пакет меняет именно его. `conv_id` из `GamePacket::Commands` отбрасывается. Нет состояния «этот conversation прошёл успешный token и принадлежит UID X», эпохи подключения или отсечения старых пакетов после смены аккаунта.

Тест воспроизводит изменение кешированного аккаунта пакетом bag **до нового token**. Если пропущен вход другого аккаунта, старый conversation ещё выдаёт отложенные команды или одновременно видны несколько conversations, чужие данные могут попасть в текущий аккаунт. Воспроизведена ошибка на границе decode→core; возникновение такой последовательности в живом PktMon не измерялось.

Исправление: session/connection identity в адаптере, запрет применения аккаунтных пакетов до подтверждения UID, отбрасывание команд старой эпохи. Сохранённый аккаунт нужен для показа кеша, но сам по себе не идентифицирует сетевой источник.

### S05. [P1, Т] Одно NaN-поле боя делает весь файл аккаунта нечитаемым

Код: [nous-hsr/src/battles.rs](../../../../Nous-sdk/crates/nous-hsr/src/battles.rs), [account.rs:161](../../../../Nous-sdk/crates/nous-core/src/account.rs#L161).

Protobuf допускает нечисловые значения `f64`. Тест передаёт `cost_time = NaN`: JSON-сериализация записывает `null`, а следующая десериализация `f64` завершается ошибкой. Весь аккаунт отодвигается в unreadable-backup, приложение получает новый пустой аккаунт. Исходный файл сохраняется, поэтому это потеря доступности данных и необходимость восстановления, а не доказанное уничтожение всех байтов.

Валидировать `is_finite()` и диапазоны до изменения состояния; изолировать повреждённую запись боя от остального аккаунта. Проверить также бесконечности, отрицательные значения и переполнение сумм.

### S06. [P1, П+К] Оверлей доверяет другому origin из-за starts_with

Код: [overlay_host.rs:402](../../../../Nous-sdk/app/src-tauri/src/veritas/overlay_host.rs#L402), [overlay_host.rs:446](../../../../Nous-sdk/app/src-tauri/src/veritas/overlay_host.rs#L446), [overlay_host.rs:503](../../../../Nous-sdk/app/src-tauri/src/veritas/overlay_host.rs#L503).

Разрешение навигации — `uri.starts_with(allowed)`. При `allowed = http://tauri.localhost` проходит и **`http://tauri.localhost.attacker.invalid/`**, хотя origin другой. Это проверено отдельным тестом эквивалентного строкового предиката. Мост `BRIDGE` внедряется при создании документов, а `WebMessageReceived` не проверяет `Source` отправителя.

Если оверлей удаётся перенаправить на такой адрес, чужая страница сможет пользоваться мостом: читать overlay-state, менять настройки и вызывать разрешённые overlay actions. В частности, в настройках есть путь экспорта и auto-export. Готового пути принудительной удалённой навигации из текущих игровых данных не найдено; эксплуатация всего WebView не выполнялась. Ошибка в самой границе origin подтверждена.

Сравнивать разобранные scheme/host/port, ограничить документ/маршрут и повторно проверять `Source` сообщения. Это соответствует [рекомендациям Microsoft по WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security).

### S07. [P1, К] Повышенные права используются для путей из изменяемых пользовательских файлов

Код: [launch.rs:171](../../../../Nous-sdk/app/src-tauri/src/launch.rs#L171), [launch.rs:298](../../../../Nous-sdk/app/src-tauri/src/launch.rs#L298), [veritas.rs:436](../../../../Nous-sdk/app/src-tauri/src/veritas.rs#L436), `nous-admin.manifest`.

Release запускается с `requireAdministrator`. Путь из `game_path.txt` проверяется только на `is_file()`, после чего «Играть» запускает его с унаследованными повышенными правами. Имя, происхождение и подпись исполняемого файла не проверяются.

При отключении Veritas путь удаления полностью берётся из `veritas.json`. Проверка SHA-256 подтверждает совпадение содержимого с записанным рядом значением, но не доказывает, что это установленный Nous `xluau.dll`: локальный процесс может изменить и путь, и хеш известного ему файла.

Условия риска: локальный процесс с доступом к пользовательскому AppData, последующее чтение подменённых настроек и действие пользователя в повышенном Nous. Повышение прав/удаление реальных файлов не выполнялись. Требуется отделить привилегированный захват от UI либо строго ограничить допустимые цели привилегированных операций; нельзя считать пользовательский JSON доверенным журналом владения файлами.

### S08. [P1, К] Установка DLL и сохранение её учёта не образуют одну операцию

Код: [veritas.rs:125](../../../../Nous-sdk/app/src-tauri/src/veritas.rs#L125), [veritas.rs:417](../../../../Nous-sdk/app/src-tauri/src/veritas.rs#L417).

DLL уже записана в папку игры, затем `state.save()` подавляет ошибки `create_dir_all`, сериализации и `fs::write`. Команда возвращает успех. После сбоя диска/прав/питания `veritas.json` может отсутствовать или содержать часть JSON; startup трактует ошибку как настройки по умолчанию с `enabled=false`.

Итог: UI сообщает «выключено, в папке игры ничего нет», но DLL остаётся и игра может загрузить её. `disable_veritas` без записи `installed` её не найдёт. Нужны атомарные настройки, возврат ошибки и восстановление/rollback установки, а также сверка реального файла с журналом при старте. Тесты не устанавливали и не удаляли DLL в настоящей игре.

Запись login в production также хранит исходный `PlayerGetTokenScRsp`, включая `authkey` и `secret_key_seed`, в Base64, а не шифрованном виде (`nous-hsr/src/recorder.rs:44`). ## Запуск, релизы и восстановление

### S28. [P2, П+К] PowerShell/CI может скрыть ошибку предшествующей команды

В [release.yml:91](../../../../Nous-sdk/.github/workflows/release.yml#L91) lint, tsc и modules-тесты выполняются последовательно в одном PowerShell step без проверки `$LASTEXITCODE` после каждой команды. Safe-repro с первой командой `exit 7` и последней `exit 0` завершился **0** даже с `$ErrorActionPreference='Stop'`. [GitHub описывает](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) добавление проверки именно последнего exit code. Поэтому успешный последний шаг может скрыть ошибку lint. TypeScript повторно проверяется сборкой, lint — нет.

Отдельно `launch.rs:227`: ветка UAC пишет исполняемый сценарий в предсказуемый `%TEMP%/nous-task.ps1`, который можно подменить между записью и повышенным исполнением. Внешний `Start-Process -Wait` не получает `-PassThru` и не передаёт exit code внутреннего PowerShell. Это касается запуска без elevation, в частности debug; release уже повышен. Реальный UAC, автозапуск и подмена temp-файла не выполнялись.

Разнести CI-команды по step или проверять native exit code немедленно. Для привилегированного действия — защищённый минимальный helper без общего изменяемого сценария и с явным результатом операции.

Дополнительные процессные пробелы:

- `concurrency: cancel-in-progress:false` не гарантирует «каждый push по порядку», как обещает комментарий. По [документации GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) обычная группа имеет один pending и не гарантирует порядок; нужно определить желаемую политику latest-only/очереди.
- `.github/**` исключён из push-trigger, отдельного PR-workflow в копии нет: правка CI может не провериться до следующего изменения приложения. Существующие браузерные проверки Veritas/UI не вызываются release workflow; три module-теста покрывают иной слой.
- `useUpdater` после неудачной установки показывает «попробуйте позже», но error-view не содержит retry, check выполняется только на старте. Для восстановления нужен перезапуск приложения. Один install также не защищён отдельным синхронным in-flight guard.
- `SnifferStatus::WaitingForLogin` при позднем запуске и `profile.source=Live` после выхода из игры не дают ясной картины свежести: нет общей инвалидации live-источника по закрытию/разрыву. Ошибка захвата не вынесена на все экраны с восстановлением.
- Экраны characters/relics остаются заглушками: после успешного входа текст «войдите в игру, чтобы загрузить» продолжает отображаться. Это незавершённая функция, которую нельзя диагностировать как неуспешный вход. Overview/map прямо сообщают о планируемой реализации.

## Что уже исправлено в SDK относительно main

Не переносить в backlog SDK прежние выводы без проверки:

- `Client` использует общий writer, pending snapshot и acknowledge; прежний off-lock saver из `main` не является текущей реализацией.
- Ошибка save возвращается, dirty/logs восстанавливаются; тест повторной записи после сбоя служит положительным контролем.
- UID аккаунта и profile сверяется с именем файла; соответствующий тест проходит.
- Сгруппированные scene entities объединяются адаптером; тест поиска игрока в группе проходит.
- Пустой инвентарь начинающего аккаунта разрешён replay-тестом SDK. Прежний ложный отказ replay в main устранён.
- Перед установкой Veritas повторно проверяются запуск игры, путь и содержимое target после загрузки. Это снижает прежнюю гонку; S08 и S27 относятся к оставшейся нетранзакционности.
