# Протокол — карта и сундуки

Проверено 02.11.2026 на игре 4.6 (reliquary v24), этаж `20211001`, прототипом `spike/hsr-sniff`.

## Что присылает сервер

| Пакет | Когда | Что внутри |
|---|---|---|
| `GetSceneMapInfoScRsp` | Игрок открывает карту локации | Для каждого этажа: счётчики сундуков по типам и **ID всех уже открытых сундуков**, включая открытые давно |
| `OpenChestScNotify` | Открыт сундук | `chest_id` |
| `GetMarkChestScRsp` / `MarkChestChangedScNotify` | Вход, изменения | Отметки сундуков (этаж, группа, объект) |

> [!warning] Поля перепутаны
> Имена полей после версии 2.6 частично обфусцированы. **Открытые сундуки лежат в `lighten_section_list`**, а не в `opened_chest_id_list`. Проверено: 15 ID = 8 обычных + 7 головоломок, совпадает со счётчиками `chest_list`. После обновлений игры сверять заново.

## Связь с датамайном

- `ExcelOutput/MazeChest.json`: список сундуков. ID = `<plane><6xx>` (например `20211601`), тип (обычный, испытание, головоломка).
- `Config/LevelOutput/SharedRuntimeGroup/Groups_P<plane>_F<floor>/*.json`: объекты этажа. У сундука есть поле `ChestID` и координаты `PosX/PosZ`.
- Неоткрытые сундуки = все `MazeChest` этажа − открытые из пакета. Координаты берутся по `ChestID`.

Проверка на живых данных: по расчёту не открыты сундуки 601 и 608. Сервер в отметках прислал ровно их, а после открытия 601 осталась только отметка 608.

## Что ещё не решено

- Перевод игровых координат в координаты картинки карты (`MapInfo`).
- Головоломки: несколько сундуков в одной точке, временные события.
- Полная картина требует один раз открыть карту каждой локации.
