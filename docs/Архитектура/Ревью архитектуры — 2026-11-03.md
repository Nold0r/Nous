# Ревью архитектуры Nous — 2026-11-03

## Цель и границы

Nous рассматривается одновременно как приложение-платформа и библиотека с API для получения данных из трафика Honkai: Star Rail. Встроенные модули приложения должны иметь возможность работать независимо от API данных HSR.

Ревью выполнено по рабочему дереву, включая незакоммиченные изменения, в предыдущем проходе Codex. Это снимок результатов того прохода, а не подтверждение состояния всех последующих изменений. Ссылки ведут на файлы; приведённые номера строк относятся к состоянию на момент ревью и могут смещаться. Исправления в рамках ревью не вносились.

P1 — существенная ошибка поведения или препятствие заявленной архитектурной цели. P2 — проблема согласованности, расширяемости или надёжности, которую следует устранить до расширения публичных контрактов.

## Основной вывод

Сейчас Nous имеет основу desktop-приложения с расширяемым интерфейсом, но самостоятельная библиотека и платформа модулей ещё не выделены. Главная архитектурная задача — разделить API данных HSR и API приложения: встроенному модулю не должна быть обязательна зависимость от перехвата трафика.

Существующее разделение `ui / shell / features`, автоматическую регистрацию экранов и предметные модели стоит сохранить. Перестройку можно проводить постепенно.

## Замечания

### 1. [P1] Самостоятельного публичного SDK Nous пока нет

**Код:** [lib.rs](../../app/src-tauri/src/lib.rs), строки 1–21; [game.rs](../../app/src-tauri/src/game.rs), строки 44–48.

Внутренние модули Rust закрыты; наружу экспортируется только `run()`, запускающий Tauri. Ядро принимает `AppHandle`, получает состояние через Tauri и связано с файловым хранилищем.

**Последствие:** внешний потребитель не может просто подключить Nous, запустить захват и подписаться на данные без загрузки оболочки приложения. Объявление `[lib]` само по себе не создаёт самостоятельный API.

**Рекомендация:** выделить публичный Rust API создания экземпляра, запуска/остановки, чтения состояния, подписок и ошибок. Tauri должен стать адаптером к этому API. Конфигурация и зависимости ядра должны передаваться явно, без обязательного `AppHandle`.

### 2. [P1] Смена аккаунта неполностью уведомляет потребителей данных

**Код:** [game.rs](../../app/src-tauri/src/game.rs), строки 64–71; [sniffer.rs](../../app/src-tauri/src/sniffer.rs), функция `emit_changes`; [game-data.ts](../../app/src/lib/game-data.ts), функция `useBattles`.

При смене UID заменяется весь `Account`, но выставляются только изменения профиля и сброс инвентаря. Мир, история боёв, прыжков и снимки тоже заменяются, однако общего события смены аккаунта нет.

**Сценарий:** если потребитель `useBattles` остаётся смонтированным при переходе с аккаунта A на B, он сохраняет бои A и начинает добавлять к ним бои B. Другие долгоживущие потребители также могут сохранять предыдущие данные до следующего соответствующего обновления.

**Рекомендация:** ввести общее событие `AccountChanged` со сбросом всех зависимых состояний. События должны содержать UID и идентификатор сессии; асинхронные ответы старой сессии следует отбрасывать.

### 3. [P2] Чтение состояния и подписка не образуют согласованный контракт

**Код:** [inventory.ts](../../app/src/lib/inventory.ts), строки 111–127; [game-data.ts](../../app/src/lib/game-data.ts), хуки `useWorld`, `useBattles`, `useGacha`, `useSnapshot`; [profile.ts](../../app/src/lib/profile.ts), функция `useProfile`.

Сначала запускается запрос снимка, затем асинхронно регистрируется слушатель. Между получением снимка и готовностью подписки обновление может потеряться. Поздний ответ запроса также может затереть более свежее состояние. Это вывод из порядка операций; отдельное воспроизведение гонки во время ревью не выполнялось.

**Последствие:** потребитель не может установить, является ли его локальное состояние актуальным, особенно при применении дельт инвентаря.

**Рекомендация:** добавить ревизии снимков и событий. При начальной синхронизации регистрировать подписку, временно буферизовать события и применять только события новее полученного снимка. При пропуске ревизии повторять синхронизацию. Простая перестановка `listen` и `invoke` не решает все гонки.

### 4. [P2] Сохранение блокирует обработку трафика и чтение состояния

**Код:** [sniffer.rs](../../app/src-tauri/src/sniffer.rs), строки 107–114; [game.rs](../../app/src-tauri/src/game.rs), строки 139–148; [account.rs](../../app/src-tauri/src/account.rs), функция `Store::save`.

Сниффер вызывает обработчик под общим mutex. Обработчик синхронно сериализует и сохраняет весь аккаунт. Обновление одной сущности может потребовать записи инвентаря, мира, снимков и истории.

**Последствие:** файловый ввод-вывод задерживает обработку следующих пакетов и блокирует запросы интерфейса. По мере роста аккаунта увеличивается риск накопления задержек. Фактическая потеря пакетов и масштаб задержек в этом ревью не измерялись.

**Рекомендация:** отделить последовательную обработку команд от сохранения. Передавать согласованные снимки или изменения отдельному worker, объединять частые записи, явно обрабатывать ошибки сохранения. Порядок обработки команд и согласованность аккаунта должны сохраняться.

### 5. [P2] Реестр экранов пока подменяет контракт модулей платформы

**Код:** [types.ts](../../app/src/features/types.ts), интерфейс `FeatureDef`; [registry.ts](../../app/src/features/registry.ts); [lib.rs](../../app/src-tauri/src/lib.rs), регистрация состояний, сервисов и команд; [App.tsx](../../app/src/App.tsx), маршруты экранов.

`FeatureDef` обязательно содержит React-компонент и категорию меню. Автономные экраны уже поддерживаются, однако фоновый модуль без экрана в этот контракт не помещается. Backend-сервисы и команды подключаются вручную в центральном файле. Общего жизненного цикла модулей нет. Компоненты маршрутов монтируются без локального `ErrorBoundary`.

**Рекомендация:** отделить `ModuleDef` от описания экрана. Модулю нужны идентификатор, необходимые сервисы, запуск/остановка, настройки, хранилище и необязательные экраны. Экран — одна из возможностей модуля. Для встроенных при сборке модулей не требуется вводить динамическую загрузку нативных библиотек.

Пример: модуль заметок получает хранилище и навигацию от платформы; модуль реликвий дополнительно запрашивает сервис данных HSR. Оба используют общий механизм регистрации. Фоновые задачи модуля не должны зависеть от того, открыт ли его экран.

### 6. [P2] Обновление хранилища допускает потерю накопленной истории

**Код:** [account.rs](../../app/src-tauri/src/account.rs), функции `load`, `load_or_new`, `save`.

Несовместимый формат или ошибка десериализации приводят к созданию нового аккаунта. Последующее сохранение может заменить старый файл. Это существующая политика обработки ошибки, а не подтверждённый случай потери пользовательских данных.

**Рекомендация:** предусмотреть миграции схемы, сохранение исходного файла при ошибке и диагностируемый результат загрузки. Версии формата хранения и публичного API следует вести независимо. Будущие пользовательские данные модулей должны иметь отдельное пространство хранения и собственную схему миграций.

### 7. [P2] Тесты обходят важнейшую границу приложения

**Код:** [replay.rs](../../app/src-tauri/src/replay.rs), функции `replay_file` и `replay_login_recordings`; [release.yml](../../.github/workflows/release.yml).

Replay вызывает обработчики отдельных подсистем напрямую, минуя `GameState::handle`. Он не проверяет смену аккаунта, формирование `Changes` и сохранение. При отсутствии записей replay успешно завершается без проверки данных. В release workflow перед публикацией нет отдельного запуска Rust-тестов и линтера.

**Рекомендация:** добавить воспроизводимые обезличенные фикстуры и проверки полного пути «команда → состояние → события», включая смену UID, повторное подключение и синхронизацию снимка с событиями. Локальный replay пользовательских записей можно сохранить как дополнительную проверку. Обязательные проверки должны запускаться до публикации релиза.

## Предлагаемые границы

| Часть | Ответственность |
|---|---|
| `nous-core` | Предметные модели, состояние аккаунта, запросы, события и ревизии; без Tauri и файлового ввода-вывода |
| Адаптер HSR | Захват, reliquary, protobuf и преобразование протокола в команды ядра |
| Платформа приложения | Жизненный цикл модулей, настройки, хранилище, фоновые задачи, команды и навигация |
| Встроенные модули | Собственная логика; доступ к данным HSR подключается по необходимости |
| Tauri-адаптер | Связь сервисов с интерфейсом через IPC |

API данных HSR и API платформы — разные контракты. Общий код обработки данных должен использоваться библиотекой и приложением без дублирования. Платформенные возможности доступны модулю независимо от работы захвата и наличия подключённого игрового аккаунта.

## Порядок следующих работ

1. Исправить согласованную смену аккаунта и контракт начальной синхронизации; покрыть их тестами.
2. Выделить ядро и публичный API, сохранив существующую предметную логику.
3. Ввести контракт платформенного модуля с необязательными экранами и зависимостью от HSR по запросу.
4. Вынести сохранение из цикла обработки трафика и добавить диагностику ошибок хранения.
5. Зафиксировать версии API, миграции и обязательные проверки релиза.

Это рекомендации ревью, а не разрешение на автоматическое выполнение всей перестройки.
